## Identification (official sources)

- RK download page (`en.rkgaming.com/download/`, API `download/drivers`): the
  RK68 HE web driver is `https://rk.hubx.pro/` (other RK HE boards use
  `drive2.rkgaming.com`; the page lists RK68 HE as unsupported by the RK web
  driver).
- `rk.hubx.pro` bundle `app-BqfTKFxh.js` device table:
  | Product | VID:PID | UUID | Protocol |
  | --- | --- | --- | --- |
  | RK68 HE | 372E:10BF | 0x110000000002 | kb_by_v3_wired, report ID 9 |
  | RK68 HE (UK layout) | 372E:10C0 | 0x11000000003C | kb_by_v3_wired, report ID 9 |
  | RK-C60 | 372E:1058 / 1042, 093A:522C | 0x110000000001 / …08 | kb_by_v3_wired |
  | R75 Pro magnetic | 372E:1042 | 0x110000000030 | kb_by_v3_wired |
- It is the BY ("BeiYing") MagneticSwitch platform that HallJoy already reads
  for IPI/QBZ (same UUID namespace `0x1100…`, report ID 9). The RK app's command
  builders include exactly HallJoy's frames: UUID `82 01 … 06`, map `83 00`,
  live read `94 05`; checksum `255 − (9 + sum)` like `ipi::Finish`.
- Key layout from the same bundle (`rk68he-layout.json`): 68 keys, physical IDs
  (`pos`) 1, 15..77, 99, 100, 102, 103; factory codes in the IPI encoding
  (`0x0D000000` = Fn, modifier bits). UK: 69 keys (+ ID 105, ISO key).

## Firmware

- `hubx.pro/api/v1/firmware/fetch` (the request the RK app itself sends) returns
  no image for RK68 HE (`…02`, `…3C`), RK-C60 or R75 Pro.
- Scan of UUIDs `0x110000000000..7F` and `0x120000000000..0F` (one throttled
  request each): 27 UUIDs have images. The latest image of each (24 packages,
  all MD5 = API hash; `downloads.json`) was downloaded; the updater EXE was
  parsed as a ZIP container (never run) and `firmware.bin` extracted (`bin/`).
- `extract_audit.py` (same method as `tools/audit_ipi_firmware.py`, register-
  independent dispatcher) — `audit.json`. ALL 24 images (AULA 2827/2829SE/2836/
  2819/2837/HERO 68 Air, IPI flash68/G67/G75/QBZ65/RAIN65/G75 PRO, Redragon
  K709PLB, M68Pro, FR_7446, TK52Y, KB901, KG18+, Royal Kludge RK_858 `372E:1043`
  and RX195 X68 / M68 HE UK `372E:10A3`) have the `94` → subcommand 2 addressed
  live-read handler with the record layout HallJoy parses (ID BE16 at byte 7,
  raw/status, secondary). Raw averaging divisor 128 or 192 varies by build.
- `rk68_layout.py`: the RK68 HE ID set is IDENTICAL to the firmware ID tables of
  FR_7446 (`…0D`), FR_7446 M68Pro (`…21`) and K709PLB (`…24`); most other
  68-key images differ only by one navigation-key ID (98 instead of 100). The UK
  set equals those plus 105.

## Conclusion

RK68 HE is very likely readable by HallJoy's existing IPI (BY) read-only path;
the obstacle is admission, not protocol. Not proven: its own firmware image is
unpublished, so its ID table and handler come from the configurator plus 24
sibling images, not from its own binary.

- The driver-image geometry is slightly irregular (hand-placed key images);
  the owner evaluates the layout visually.
